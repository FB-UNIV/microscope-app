# Moticam capture goes through the Motic SDK, not cv::VideoCapture

The README's plan was "try `cv::VideoCapture` against the Moticam first, Motic SDK only as fallback". The Motic driver shipped with MotiConnect 1.0.1.9 (`MoticUSBCamera.inf`, driver 3.0.0.1) binds every Motic USB camera — USB2, USB3, Moticam580, HDMI and Vision models, VIDs `0634`, `232F`, `04B4`, `4255` — to **WinUSB** with a private interface GUID `{9E234069-2033-4498-8318-79CC4BC58E66}`. WinUSB devices are not exposed through DirectShow or Media Foundation, so `cv::VideoCapture` cannot open them. The SDK is therefore the primary path, not the fallback; OpenCV stays as a backend for any UVC camera (lab webcam, demos) and the file-replay backend covers no-camera work and CI.

**Consequences:** Capture sits behind `ICamera` (`include/camera.hpp`), selected by configuration (`makeCamera`), so the Motic backend is one new class once the developer SDK (headers + DLLs + licence — MotiConnect is the end-user app, not the SDK) is in hand. Until then `makeCamera({"motic"})` fails loudly rather than falling back silently. Linux support (ADR 0001) now hinges on whether Motic ships a Linux SDK, not on V4L2. If the exact purchased model turns out to enumerate as a UVC "Camera" device in Device Manager, the OpenCV backend works for it and this ADR's urgency drops, but the abstraction still stands.
