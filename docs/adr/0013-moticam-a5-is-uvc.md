# The lab's cameras are Moticam A5, which are UVC: capture through the OpenCV backend

**Status:** supersedes in part [ADR 0011](0011-motic-capture-via-sdk-not-uvc.md), for the Moticam A5.

The purchased cameras are confirmed to be Moticam A5, which enumerate as standard USB Video Class devices. ADR 0011 made the Motic SDK the primary capture path because MotiConnect's driver binds Motic USB cameras to WinUSB; that remains true for those models, but not for the A5. Capture therefore goes through `OpenCvCamera` (`cv::VideoCapture` → DirectShow or Media Foundation on Windows, V4L2 on Linux): no SDK, no SDK licence, and the optional Linux build from ADR 0001 becomes plausible again since UVC works over V4L2. The `"motic"` backend name stays reserved and fails with an explanation, for any future WinUSB-only Motic model.

**Consequences:** A workstation's camera config is backend `"opencv"` plus capture API, device index and requested frame size. UVC cameras often open at 640×480 unless a size is requested, and Windows exposes exposure/gain more reliably through DirectShow than Media Foundation — both to be confirmed on the real A5 with `tools/camera_probe` before the Qt UI hard-codes anything. A UVC device can be opened by one program at a time, so MotiConnect must be closed while the app captures. Device index is not a stable identity on a PC with several cameras (built-in webcam + A5); if that bites, select by device name in the Qt UI (QMediaDevices) rather than by index. UVC exposes white balance as a colour temperature, not the per-channel R/G/B gains the legacy app stored, so `setWhiteBalance(gains)` stays unsupported on this backend; add software gains only if teachers need them.
